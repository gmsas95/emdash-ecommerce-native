title: Theme Composition
description: Extend a Commerce storefront while keeping structure in source and client data in EmDash.

A Commerce theme is a working Astro application. Its source defines the storefront structure and the server-rendered behavior around EmDash and Commerce data. The generic Commerce Cloudflare starter uses Page Composer for bounded section composition and `@emdash-cms/theme-tokens` for approved visual decisions; neither is a freeform code or visual-canvas runtime.

## Ownership boundary

Keep these responsibilities explicit:

| Theme source owns | EmDash CMS/plugin owns | Commerce Core owns |
| --- | --- | --- |
| HTML and semantic markup | Site identity, title, tagline, and logo/media references | — |
| Server and browser behavior | Portable Text and other editorial content | — |
| Responsive layout rules and breakpoints | Media assets and media metadata | — |
| Accessibility semantics, labels, focus behavior, and keyboard interaction | Menus, validated theme settings, and component-variant selections | — |
| Commerce integration, product/cart/checkout targets, and data-fetching glue | Page Composer layout instances and section settings | Published catalog: products, variants, prices, inventory, carts, checkout, orders, and payment state |
| Safe empty states and error boundaries | — | — |
| CSS that consumes emitted theme variables | — | — |

A client onboarding changes CMS data, Commerce catalog data, media, menus, Page Composer settings, and approved theme tokens. It should not require copying or editing the reusable Astro source.

## Theme-owned structure

The starter's source provides the common storefront shell and commerce routes:

1. utility/site message area;
2. header with identity, navigation, search, and cart;
3. hero and CMS-managed media;
4. product-first catalog and featured-product views;
5. bounded content/trust/story sections;
6. newsletter or contact CTA; and
7. footer with identity and navigation.

The shell and CMS content render useful HTML on the server. Catalog, product, cart, and checkout data are fetched and hydrated client-side through Commerce APIs, while the surrounding route structure remains theme-owned. Theme code owns the markup, interaction state, responsive behavior, and accessible semantics for both layers.

Theme components consume variables such as `--theme-color-brand`, `--theme-font-heading`, and `--theme-layout-contentWidth` and switch only approved variants. Theme-token settings do not accept client-authored HTML, CSS, JavaScript, class names, arbitrary remote URLs, pixel coordinates, or copied prices/inventory. Page Composer section schemas have their own content fields, which may include values such as `imageUrl` and `ctaHref`.

## EmDash-owned data

EmDash site settings provide the site's identity and logo. Collections provide pages, Portable Text, story/content entries, and other editorial fields. Media references resolve through the CMS media library. Menus provide navigation. Commerce Core remains authoritative for product details, variant selections, prices, inventory, cart totals, checkout, orders, and payment state.

A product section stores a Commerce product reference; its surrounding section is server-rendered, while the current catalog data is fetched by the client Commerce runtime. It must not persist a copied price or inventory value in a Page Composer layout or editorial entry. If a reference is missing or unavailable, the registered renderer uses its safe empty state rather than executing unknown content.

## Bounded Page Composer sections

Page Composer stores a versioned layout tree, section IDs, validated settings, registered section types, responsive presets, and visibility. A layout is data, not serialized markup:

```ts
type PageLayout = {
  version: 1;
  sections: SectionInstance[];
};

type SectionInstance = {
  id: string;
  type: string;
  settings: Record<string, unknown>;
  layout?: {
    desktop?: "stack" | "split" | "three-column" | "center" | "wide" | "narrow";
    tablet?: "stack" | "split" | "three-column" | "center" | "wide" | "narrow";
    mobile?: "stack" | "split" | "three-column" | "center" | "wide" | "narrow";
  };
  visibility?: { desktop?: boolean; tablet?: boolean; mobile?: boolean };
};
```

The registry supplies each section's type, label, category, settings schema, supported presets, and renderer. The Commerce starter includes bounded patterns such as hero, image-text, feature columns, FAQ, product grid, featured product, category grid, reviews, announcement, and newsletter. An extension can register a new section with its own schema and renderer; an unknown section is rejected or omitted safely.

The trusted editor supports insertion, section-tree reordering, duplication, removal, validated properties, constrained responsive presets, visibility, and preview. It does not persist arbitrary HTML, CSS, JavaScript, absolute positioning, pixel coordinates, unrestricted nested layout trees, or editor-authored order/payment state. Portable Text remains the editorial rich-text model.

## Responsive and accessible behavior

Responsive rules belong to theme source, not to client data. The source chooses how headers, grids, controls, media, typography, and spacing reflow at desktop, tablet, and mobile sizes. Presets constrain section intent; they do not let an editor inject breakpoints or CSS.

Every renderer should preserve semantic heading order, meaningful landmarks, text alternatives for media, visible focus, keyboard access, touch-sized controls, and usable forms. Validate a layout before selecting a renderer, render sections server-side with page context, and provide an accessible fallback or safe omission for unavailable content. Theme motion must always honor `prefers-reduced-motion: reduce`; the theme-token emitter provides the baseline override.

Typography is semantic rather than tied to a component's hardcoded brand family: `display` serves hero/marketing headlines, `heading` serves page and section headings, `body` serves long-form content, and `ui` serves navigation, labels, prices, forms, and metadata. Select approved registry IDs through Theme Settings; use Google Fonts preview only for iteration and self-host approved files in production. See [Theme tokens](/guides/theme-tokens/) for the registry and delivery contract.

## How to extend without client forks

Use this sequence when a site needs a new presentation or capability:

1. Put client copy, media, and navigation in EmDash collections, settings, menus, and media. Put products, variants, prices, inventory, carts, checkout, and orders in Commerce Core.
2. Use existing theme variants, token settings, and registered Page Composer sections where they express the requirement.
3. If a reusable structural pattern is missing, add a typed section definition and server renderer to the theme source; keep its settings schema bounded and its content references explicit.
4. Add responsive and accessibility behavior in that source renderer, and consume theme-token variables instead of embedding brand values.
5. Keep payment/provider behavior behind Commerce Core's documented bridge and provider-plugin boundary.
6. Update the shared template and seed/schema contract rather than copying the template into a client-only fork.

Do not solve a one-site content request by adding conditionals keyed to a client name, a product ID, or an environment flag. Do not expose repository access or arbitrary code execution in the production theme. A future repository/design concierge workflow is a separate, sandboxed development workflow; it is not Page Composer or the theme-token MCP execute tool.

## Rendering rules

1. Validate the layout before selecting a renderer.
2. Render the validated section shell server-side with page context; let catalog, product, cart, and checkout widgets hydrate through the Commerce client where the starter uses client components.
3. Read current published Commerce data for product references.
4. Keep draft Commerce records private; preview must not publish draft products.
5. Preserve semantic headings, keyboard interaction, text alternatives, visible focus, responsive behavior, and reduced-motion behavior.
6. Emit normalized analytics events from stable theme targets; theme code does not call provider pixels directly.

Themes expose stable semantic product, cart, checkout, search, and lead targets. The analytics runtime consumes normalized events from those targets and independently handles consent and provider adapters.
